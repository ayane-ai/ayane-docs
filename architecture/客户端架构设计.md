# 客户端架构设计

上位架构：[项目整体架构设计](项目整体架构设计.md)

产品目标：[产品愿景与总纲](../product/产品愿景与总纲.md)

## 1. 仓库定位

`ayane-client` 是 Android、Desktop、iOS 共用的统一跨平台客户端仓库。

客户端仓库以 [Ci-Yin/NomiKit](https://github.com/Ci-Yin/NomiKit) 为基础搭建，沿用 Kotlin Multiplatform、Compose Multiplatform、模块化和单向依赖方式。KMP 是内部实现方式，不作为仓库名称的一部分。

客户端只负责用户端体验、平台能力、会话通信和身体适配，不负责服务端推理、核心记忆或 Unity 工程实现。


### app:shared

- 跨端页面、导航、资源和应用状态。
- Session、Identity、Memory 和会话展示。
- API、WebSocket 和 Action Event 消费。
- 共用 Compose UI 和客户端业务编排。

### Android

- Android 应用入口、生命周期和权限。
- 麦克风、音频焦点、通知和前台服务。
- Android 本地缓存和网络恢复。
- Android Unity Library 的加载和生命周期适配。

### Desktop

- Phase 1 主验证端。
- Desktop 窗口、系统托盘和全局快捷键。
- 麦克风、音频播放、调试日志和开发工具。
- Desktop Unity Runtime 的启动、连接和异常恢复。

### iOS

- iOS 应用入口、生命周期和权限。
- `AVAudioSession`、音频播放和推送。
- iOS 本地缓存和网络恢复。
- iOS Unity Framework 的加载和生命周期适配。

## 3. 共享层边界

共享层负责：

- 网络和会话状态。
- Identity、Memory、Session 和 Action Protocol 数据模型。
- Repository、UseCase、MVI 状态和事件。
- 序列化、业务错误和平台能力抽象。
- Unity Bridge 抽象和动作映射。

共享层不负责：

- Agent Runtime 的服务端实现。
- 云端模型调用和 API Key。
- Unity 工程源码。
- Android、Desktop、iOS 之间的互相调用。

## 4. Unity Bridge

每个平台拥有自己的 Unity Bridge：

```text
Agent Action Protocol
        ↓
平台 Unity Bridge
        ↓
Unity Embodiment API
        ↓
Unity Runtime Artifact
```

Bridge 负责：

- 将通用动作协议映射为 Unity 身体 API。
- 处理平台生命周期和资源加载。
- 管理连接、异常恢复和版本兼容。
- 屏蔽 Desktop、Android、iOS 的 Unity 集成差异。

## 5. 依赖规则

客户端依赖：

- [Contracts 架构设计](Contracts架构设计.md)
- [AgentService 架构设计](AgentService架构设计.md) 所描述的 Client API
- `ayane-unity-embodiment` 发布的固定版本产物

客户端禁止：

- 直接访问后端数据库。
- 直接调用云端 LLM。
- 直接依赖 Unity 工程源码。
- 使用 Git Submodule 作为长期 Unity 依赖。
- 让 Android、Desktop、iOS 互相依赖。

## 6. 发布和验证

- Android、Desktop、iOS 使用独立 CI 和发布流程。
- 共享层变更必须验证三个平台。
- Unity 产物通过版本号接入，不跟踪 Unity 仓库分支。
- 客户端发布前检查 Contracts 版本、服务端兼容性和 Unity 产物版本。
- Desktop 优先完成完整闭环，Android 和 iOS 按平台能力逐步接入。
