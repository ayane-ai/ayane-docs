# ayane-docs 文档维护规则

适用范围：整个文档仓库。用户在当前任务中的明确要求优先于本规则。

1. **先读相关文档**：修改前阅读产品总纲、项目整体架构及本次涉及的仓库架构，确认已有目标与决策。
2. **保持目标一致**：产品总纲约束整体架构，整体架构约束仓库架构；调研建议未经确认不得成为正式决策。
3. **最小修改**：只处理用户指定范围。重命名同步修复链接，目录整理不改写正文，不顺手收敛章节或重新设计架构。
4. **保留已有内容**：保留用户修改、图表、代码块和示例；不因主题相近而合并文档，不以较新的导出直接覆盖正式文档。
5. **统一命名和目录**：客户端仓库名为 `ayane-client`；产品、架构、调研分别放入 `product/`、`architecture/`、`research/`。仅根目录使用 `README.md`，其他目录使用中文入口文档。
6. **架构文档只讲框架**：描述职责、边界、依赖和演进；除用户明确要求外，不新增实现代码示例。
7. **保持系统边界**：Android、Desktop、iOS 共用基于 NomiKit 的客户端仓库，Desktop 为主；后端调用云端 OpenAI-compatible API；管理后台独立；Unity 独立发布版本化产物，不依赖 Contracts，由客户端 Bridge 负责 Agent Action Protocol 到 Unity Embodiment API 的映射。
8. **链接和 Notion 层级**：本地文档使用相对链接，移动后修复引用。Notion 父子关系遵循 `architecture/文档仓库架构设计.md` 中的中文入口映射；入口文档作为父页面正文，交叉链接不改变页面归属。
9. **同步有明确范围**：仅在用户要求时同步 Notion；同步前比对差异，不自动覆盖远端独立修改，不因本地文件消失而删除远端页面。
10. **流程图表达清楚**：区分运行时调用、数据流和发布依赖，箭头标明含义；视觉调整不能改变架构关系。未实际渲染时，只报告静态检查结果。
11. **调研标明证据**：区分已确认事实、建议和待验证事项；项目能力、许可证及版本信息附官方来源和核查日期。
12. **验证与交付**：检查相对链接、命名、修改范围和正文保留情况；验证结论必须来自实际检查。默认不提交、不推送、不创建远程仓库或 PR。
